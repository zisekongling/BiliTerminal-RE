> 用户原话：「我这边速度和进度显示的都非常不准确」。改前三条根因：进度按写死的阶段权重摊派（4K 视频流下完才 52%）、速度全局只有一个采样器（每行显示同一个总速度）、全局累计字节可被回滚（采样撞上回滚显示成 0）。

## H13 单任务进度必须等于「已下 / 总大小」

- **怎么做**：挑一条 **1080P 及以上、时长 10 分钟以上**的视频下载（DASH，会同时下视频流与音频流）；盯着下载列表里这一行的百分比与「已下 / 总大小」两段数字。
- **应该看到**：①「已下 / 总大小」两个数字都随下载递增，**总量从一开头就是终值**（不再从 0 慢慢长）；②百分比与「已下 ÷ 总大小」目测对得上，**视频流下完的那一刻不会停在 52% 附近**，而是继续一路走；③音频流下完后进度直接到 100%，随后状态变成「合并中」并停在那里直到合并完成；④合并结束后这一行从列表消失（既有行为）。
- **不算 bug**：开头 1~2 秒可能显示「准备中...」或 `--`（要先 HEAD 探一次两条流的大小）；如果这条线路拒绝 HEAD，会退回按阶段估算，总大小可能显示成当前文件的字节数——这属于兜底路径，仍能下完。
- **AI 半自动**：`adb logcat -s "DownloadService"` 可读 `文本更新了 百分比` 一类日志与 `HEAD 探测文件大小失败`；百分比与字节是 UI 文本，`adb shell uiautomator dump` 能读到行内文案，但「对得上」需人判。
- **预计**：4 分钟

## H14 并行多任务时每行速度各不相同，总速度约等于各行之和

- **怎么做**：同时下载 **3 条**不同大小的视频（在详情页连点多条「缓存」，或下载列表里同时进行）；观察 3 行的速度文字，再对比底栏的总速度。
- **应该看到**：①三行速度**互不相同**（改前三行显示的是同一个数字）；②底栏总速度 ≈ 三行之和（同一数量级即可，不同流速率差异大）；③某条下完后，它的那行消失、总速度相应减少，**剩下的行速度不变**。
- **不算 bug**：速度有 500ms 采样窗口 + 指数平滑，跳变后 1~2 秒才稳定；任何一条停滞超过 2.5 秒，它的行速度会显示 0 而不是上一个残值。
- **AI 半自动**：`adb shell uiautomator dump` 可取每行 `holder.speed` 的文本与底栏 `textTotalSpeed`；把三行数字加起来与底栏比对即可。
- **预计**：2 分钟

## H15 总进度条不回退、ETA 收敛

- **怎么做**：下 3 条大小不同的视频，全程盯底栏：总进度条、`已完成/总数 (xx.x%)`、ETA（剩余时间）；中途**暂停一条再恢复**，最后等全部下完。
- **应该看到**：①总进度条**单调前进**，某条任务下完消失的那一刻不会往回掉；②百分比与「已完成/总数」对得上（按字节加权，所以下完小文件时百分比变化很小，这是预期）；③ETA 在速度稳定后基本收敛、不来回跳；④暂停全部任务后速度显示 `--`、ETA 显示「计算中...」；⑤全部下完时提示下载完成，底栏隐藏（既有行为）。
- **不算 bug**：ETA 在开头 1~2 秒显示「计算中...」；单条任务暂停时该行速度变 0、总速度相应下降，但总进度条不动。
- **AI 半自动**：`adb shell uiautomator dump` 读底栏三个控件的文本，间隔 10 秒采样 3 次比对是否单调；ETA 是否「合理」需人判（可与剩余字节 ÷ 总速度粗算比对）。
- **预计**：3 分钟

## H16 封面 / 字幕 / 弹幕不计入任务进度

- **怎么做**：下载一条**带封面与弹幕**的视频（番剧更容易有字幕），盯进度百分比穿过「正在下载封面」「正在下载弹幕」这两个状态文案的时刻。
- **应该看到**：①状态文案会切到「正在下载封面 / 弹幕」，但百分比**不会因为这些小文件而跳变**（改前封面占 0→4%、弹幕占 7%→15%，会突然蹿一段）；②这些小文件下完后进度继续按视频/音频字节平稳前进；③最终视频、封面、弹幕、字幕文件都在缓存目录里（功能本身没被改坏）。
- **不算 bug**：附件下载失败不影响主任务（既有语义，只记日志）。
- **AI 半自动**：`adb shell ls -l "<缓存根>/<任务标题>/"` 确认封面（`.jpg`/`.png`）与弹幕（`.xml`）存在；百分比不跳变需人看。
- **预计**：1 分钟

## H17 兜底路径（普通 MP4 / 探测失败）仍能显示进度，且进度不倒退

- **怎么做**：①在播放设置里把清晰度压到 **360P/480P**（会走单文件 MP4 而非 DASH），下一条短视频；②再挑一条线路明显较慢的长视频（或把 Wi-Fi 调弱），观察网络抖动 / 分片重试时的进度。
- **应该看到**：①MP4 单文件任务进度同样按字节平稳走、总大小一开始就是终值；②网络抖动或分片重试时，百分比**停住但不回退**（改前分片回滚会让进度条倒退）；③速度在抖动时下降、恢复后回升，不出现负值或荒唐的大数字。
- **不算 bug**：分片模式下进度每 200ms 更新一次，抖动时可能几秒不动；如果线路拒绝 HEAD，总大小退化为「当前文件字节」，进度仍会前进。
- **AI 半自动**：`adb logcat -s "DownloadService"` 看 `分片下载 ... 重试` 与百分比日志；进度是否回退用 `uiautomator dump` 间隔采样比对。
- **预计**：2 分钟

## 附：容易误报的三点

1. **速度偶尔显示 0**：单条任务停滞超过 2.5 秒就归零（这是有意的，改前会把旧值一直挂着）。
2. **总速度不等于各行速度之和**：每条任务的采样时刻不同，瞬时值有偏差，看 2 秒内的大致关系即可。
3. **小文件下完总进度只动一点点**：总进度按字节加权而非按任务个数（改前的口径），例如 3 条任务里有 1 条 500MB、2 条 5MB，下完两条小文件总进度只前进约 2%。
