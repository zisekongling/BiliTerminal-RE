# 测试分工：谁测、测到哪、什么时候交给人

> 触发：改完代码要验证 / 想打开模拟器 / 准备说「测过了」。常驻摘要见 `AGENTS.md`「每个改动都守」；设备命令与环境坑见 `docs/review/agent-test-guide.md`；发版前人测清单见 `docs/review/real-device-regression-checklist.md`。

## 1. 唯一判据：证据能不能被机器读出来

**动手测之前，先回答一句：这条结论的证据长什么样。** 证据能被读出来就 AI 测，只能看/听/感觉就交给人——这与改动大小无关。

| 证据形态 | 例子 | 谁测 |
| --- | --- | --- |
| 退出码 / 测试报告 | `assembleDebug` 成功；`app/build/test-results/**/*.xml` 里 `<failure>` 为 0 | AI |
| 日志原文 | `MsgUtil>showMsg: 还没有登录喵~`；`PlayerActivity>initAudioTrack: …选择=EXTERNAL` | AI |
| 控件树文字 / bounds | `uiautomator dump` 里的 `text=` / `content-desc=` / `bounds=` | AI |
| 落盘产物的结构 | `merge` 命令回的 `tracks=2` / `samples=N` / `durationUs` | AI |
| HTTP 状态码与响应体 | `http.log` 的 `-> 200 (312ms)`、响应体首段 | AI |
| **画面**：好不好看、字有没有被切、颜色搭不搭、有没有错位 | 布局挤了、文字截断、主题色刺眼 | **人** |
| **声音**：音轨选错、爆音、音画不同步 | 不同频率的 `sine` 造样本靠耳朵判 | **人** |
| **手感 / 流畅度**：跟手、误触、掉帧、动画顺不顺 | 模拟器帧率与真机无关 | **人** |
| **主观取舍**：这样设计好不好用、新文案读起来顺不顺 | — | **人** |

## 2. 三级验证：按成本排队，够用就停

| 级别 | 谁 | 做什么 | 单次成本 | 什么时候必须做 |
| --- | --- | --- | --- | --- |
| **L0 静态** | AI | 编译 + 单测 + `git show --stat` 自查 | 一次构建 | 每个改动，无例外 |
| **L1 设备可观测** | AI | 装包后用调试桥拿**日志 / 控件树 / 产物结构**做断言 | 装包一次 + 每条 ≤1 分钟 | 判据落在上表前五行 |
| **L2 人工验收** | 人 | 按交接单点屏幕、看画面、听声音 | 人的时间 | 判据落在上表后四行；发版前 |

判定顺序：**先 L0 全绿，再问 L1 有没有机器可读的判据；没有就直接 L2**。不许因为"想显得测过了"去降级补测。

## 3. L1 的预算与止损（硬规则）

- **两轮上限**：同一条结论最多试 2 轮，每轮 ≤10 分钟、≤15 条 adb 命令。够了就停，不要"再试试"。
- **失败即交接**：两轮拿不到机器可判读的结论 → 停止，写交接单（§5），并在 `docs/review/fix-progress.md` 写「未验证：<该验什么> / AI 为什么测不了」。
- **同因止损**：同一种手法失效两次就换级别，不要换写法硬试。MuMu 的 `screencap -d <id>` 对任何 display 都回 `Failed to take screenshot. Status: -2`（26.10.27 实测，`adb root` 也一样）——**副屏截图这条路是死的**，别再试。
- **禁止自由探索**：不许在设备上翻菜单找功能。目标页一律由调试桥 `--es cmd start` 直达；直达不了就是「AI 测不了」，交人。
- **未复现 ≠ 通过**：连续两次复现不出记「未复现」并交人；不许把失败归给环境之后当成通过。
- **装包核对**：每次 L1 前确认设备上是本次构建的包（`pm dump <包名> | grep -i <本次新增的类名>`）。26.10.29 就因为测了设备上的旧包，把有效修复判成了「修复无效」。

### 3.1 先把「看屏幕」降级成「读日志」

大部分所谓"只能看"的条目其实有机器可读的替身，**先找替身，找不到才交人**：

| 原判据 | 机器可读替身 |
| --- | --- |
| 屏幕上弹了什么提示 | `adb logcat -s "MsgUtil>showMsg"`（原文输出，不用 OCR） |
| 页面跳没跳到目标页 | 调试桥 `start` 之后再 `top` 复核——**`start` 回 OK 只代表没抛异常** |
| 功能有没有真的执行 | `logs/rebili.log` 里对应 `类名>方法名` 的 tag |
| 请求成没成功 | `logs/http.log` 的 `-> 200` / 响应体首段；注意 `http` 命令的 `appheaders` 默认 false，未登录 + 模拟器上会稳定 -412 |
| 下载 / 合并对不对 | `merge` 的返回值只能当参考：**回 OK 但 `tracks<2` 或 `samples=0` 就是回归** |

### 3.2 唯一不能降级的：登录态写操作

关注、收藏、投币、评论、私信、删除、定时发布——日志只能证明"本地分支走了"，证明不了"服务端真的改了"，而这些操作会改动用户的真实账号。**这类条目一律归人测**，不要为了凑 L1 去写。

## 4. AI 不做的事（做了也不算数）

| 不做 | 为什么 |
| --- | --- |
| 截图判颜色 / 判布局 / 判文字是否截断 | 手表屏窄；MuMu 副屏截不到图（实测 `Status: -2`）；OCR 结论与目视结论不是一回事 |
| 听声音（音轨、爆音、同步） | 没有可读证据 |
| 判手感、流畅度、掉帧 | 模拟器帧率与真机无关，结论不可迁移 |
| 登录态写操作（关注 / 收藏 / 投币 / 评论 / 私信 / 删除 / 定时发布） | 会改动用户真实账号数据，且服务端状态不可回滚 |
| 长链路多步交互（如「下载 → 缓存页 → 多选 → 批量删除」） | 步骤越多越容易中途走错并把走错当成失败 |
| 真实网络环境相关的判定（弱网、切 Wi-Fi/移动数据、锁屏、省电） | 环境造不出来，结论不可信 |
| 对新文案的「顺不顺」下结论 | 属主观取舍 |

## 5. 交接单：把 L2 交出去时怎么写

**什么时候写**：本次改动有 L2 项，或 L1 止损退出时。写给「不懂代码的人」也能照做，**范本是 `docs/review/manual-test-guide-261106.md`**。

该范本自 26.11.06 起是**人机双轨**写法：每条末尾带一行结论性标注——
`AI 断言`（可直接抄的 adb / logcat 断言，AI 能自己跑完并判定）、
`AI 半自动`（AI 只能验一半，另一半写清人要看什么）、
`AI 判不了`（写明为什么机器做不到，比如中文输入、真实账号写操作、蓝牙/来电/切网、纯画面）。
**新写的交接单沿用这个结构**：同一条用例既给人照着点，也能被下一个 agent 直接执行，不必二次翻译。

硬要求：

- 一次**不超过 8 条**；超过 8 条说明这次改动该拆了，先拆。
- 每条四段：**怎么做**（从哪个页面点哪几下）/ **应该看到** / **不算 bug**（已知限制）/ **预计多久**。
- 开头写清装哪个包、版本号与 commit、要不要登录、要不要特殊条件（耳机、关 Wi-Fi、相册照片、另一台设备）。
- **只写人才能判的条目**。L1 已经验过的东西不要塞进来，浪费人的时间。
- 涉及发版验收或人不在同一台机器上时，再补 4 项防扯皮信息：**用例编号**（对上回归清单的条目号）、**APK 的 md5**、**设备形态**（手表/手机、方屏/圆屏、Android 版本）、**失败时交什么**（截图/录屏 + 抓日志的命令 + 复现率）。

模板：

```markdown
# <版本> 人工验收单（<n> 条，约 <x> 分钟）

- 安装包：`app/build/outputs/apk/coexist/debug/app-coexist-universal-debug.apk`
- 版本：`versionName <YY.MM.DD>` / commit `<sha>`
- 前置：<是否登录 / 耳机 / 关 Wi-Fi / 相册一张照片 / 需要另一台设备>
- 回结果：通过写 `- [x]`；不通过留空，并在旁边写一句「看到的是什么」

## H01 <一句话说清这条验什么>

- **怎么做**：<入口 → 点哪 → 点哪>
- **应该看到**：<可观察的结果，写"数字要变""文字要出现"这种能对答案的话>
- **不算 bug**：<已知限制；没有就写「无」>
- **AI 断言**：<能读日志/控件树的那一半写断言；另一半写「人判：<看什么>」>
- **预计**：<30 秒 / 2 分钟>
```

## 6. 结论写回哪里

| 测了什么 | 写哪 |
| --- | --- |
| AI 的 L0 | 不用单独写，提交说明里带一句「`assembleDebug` + 单测通过」即可 |
| AI 的 L1 | `docs/review/fix-progress.md` **一行**：级别 + 证据（命令、关键日志原文、退出码）。不许只写「已验证」而不给证据 |
| 人的 L2 | 人回填后，把结论并入 `docs/review/fix-progress.md`，并注明「人测」 |
| 没测 | **必须显式写「未验证：<项>」**，且该条目必须出现在交接单里。**不许写「应该没问题」** |

发版前的人测范围 = `docs/review/real-device-regression-checklist.md` 的 **260 条**（实测物理条目 = 260，唯一编号 1–258，编号 215 / 216 各重复一次）+ 当版人工验收单。AI 在发版前只负责：clean 后 `assembleRelease` 两个 flavor 都出包、单测全绿、`git show --stat` 逐条核对提交内容。

## 7. 为什么这么改（26.11.06）

旧规则是「涉及播放器 / 网络 / UI 时序的改动一律装 MuMu 跑一遍」。这条规则在真机上撞了三件事：

1. **AI 没有眼睛和耳朵**。画面、声音、手感这三类占真机测试的大头，AI 只能靠截图和猜，来回折腾之后给出的「已验证」并不可信，反而比不测更危险。
2. **模拟器环境本身是坏的**。MuMu 把应用丢到每次新建的副屏、`screencap` 对所有 display 失败（`Status: -2`）——历史上大量时间花在这上面，收获为零。
3. **有些测试只有人做才划算**。设置页点十下、看颜色变没变，人 30 秒，AI 要装包 + 广播 + dump + 比对，还经常测的是一个旧包。

所以分界线不是「重要 / 不重要」，而是**「证据读不读得出来」**：读得出来的 AI 做并且必须给证据；读不出来的交人并且必须写清条目。两条都要落到 `fix-progress.md`，区别只在于「证据」还是「未验证」。
