# 改前必查的已知坑

> 触发：准备改 API 解析 / 通知 / 下载 / 播放器 / 弹幕 / 清单 / 列表 adapter / 跨包 id / 伪装与顶栏手势。**完整清单见 `docs/architecture-map.md` 第 7 节**；这里是仍存在、且踩过就会出事的那批，每条都标了实测/线上事故依据。

## API 与数据

- 视频卡片解析**重复 21 处**（`RankingApi`/`RecommendApi`×4/`WatchLaterApi`/`SearchApi`×3/`SeriesApi`/`FavoriteApi`×2/`UserInfoApi`/`HistoryApi`/`BangumiApi`/`MessageApi`×3/`DynamicApi`×2/`VideoInfo.java`），改一处要 grep 其余。旧文档写「7 份」、26.08 快照写「19 处」，26.10.04 实测 21 处（`SearchApi` 的番剧搜索分支与 `DynamicApi:826` 为漏计项）。
- `PlayerApi.java:308` 的 `fnvar` 应为 `fnver`；`DanmakuApi.java:93` 的 `segment_index` 起始值与注释不符（`:80` 的 javadoc 说从 0 开始，调用点 `:133`/`:144` 实际从 1 起）。
- `SettingsKeys.PLAYER` / `PLAY_QN` 已收敛（26.10.04 批次 4）：13 处字面量全部改调常量、`SharedPreferencesUtil.player` 死字段已删，**新代码不要再写 `"player"` / `"play_qn"` 字面量**；`SettingMainActivity.kt:118` 的 `"player"` 是分组 id 不是 SP 键，别顺手替换。其余键（`mid` 等）仍有字面量（详见 `docs/architecture-map.md` §7.12）。
- **`model/Dynamic` 的 `stats` 可空，用前必须判空**（26.10.05 线上崩溃）：`DynamicApi.analyzeDynamic` 在 `DYNAMIC_TYPE_NONE`（动态已删除/被屏蔽）时会**在填充 `module_stat` 之前提前 return**，部分动态类型也没有 `module_stat`，所以 `stats` 会是 null（`userInfo` 则无条件赋值，非空）。渲染卡片时 `DynamicHolder` 自己判空，详情页这类「直接取字段」的消费点要调 `dynamic.ensureDetailFields()`（只补 null、不覆盖已有值）。**别在 `analyzeDynamic` 里统一补空 `Stats`**——`DynamicHolder` 正是靠 `stats == null` 来隐藏点赞区的。
- **私信发图（`msg_type=2`）的 content 有硬格式**（26.10.04 批次 5 新增）：`url` 必须是 B 站图床地址（否则 21037「图片格式不合法，不要调戏接口啦」），`width`/`height` 必带（缺了接口不报错、客户端显示异常），`size` 单位是 **KB**。组装一律走纯函数 `PrivateMsgApi.buildImageContent(...)`，别手拼 JSON（详见 `docs/architecture-map.md` §7.14）。
- **`model/` 里 `VideoFolder`/`VideoMeta`/`LocalVideo` 实现 `Parcelable`，且字段名就是磁盘 JSON 存储格式**：删改字段必须两端同步。
- **评论写接口的 `type` 是「评论区类型」，不是稿件类型**：`ReplyAdapter` 里同时有 `oid`/`type`/`replyType` 三个字段，评论区的点赞、置顶、删除**一律传 `replyType`**；传 `type`（视频类型）会让动态/专栏的评论被服务端拒。
- **`NetWorkUtil.FormData.toString()` 会对值做 URL 编码，且底层是 `HashMap`（顺序不确定）**（26.10.27 写请求体单测时踩到）：纯函数单测里断言请求体必须①拆成 key→value、②用 `URLDecoder.decode` 还原中文，**不能断言整串**。另外 `FormData` 的 `autoAddAccessKey` 默认 **false**，只有显式打开才会在 `toString()` 里读 `SharedPreferences`——想让「拼请求体」保持纯函数可测，csrf / access_key 这类要在**调用方**补，别塞进被单测直接调的函数里。
- **R8 混淆过的堆栈必须用同版本 `mapping.txt` 还原，别靠「猜帧」**（26.10.28 血泪）：release 开了 `minifyEnabled`，堆栈里类名/方法名全是 `E0.e.run` / `q0.Y.l`，只有 Activity 这类入口类名幸存。第一次只凭幸存帧推断，结论**全错**（把「Glide 已销毁」的锅扣给了用 application context 的 Opus/私信）。正确做法：`./gradlew.bat :app:minify<Flavor>ReleaseWithR8`（不需要签名，本机没 keystore 也能出）→ `app/build/outputs/mapping/<flavor>Release/mapping.txt`。**两个坑**：①mapping 只对同一次构建有效，跨版本只能解方法名、**行号千万别用**；②R8 会做 **lambda 类合并**，同一 synthetic 类可能挂着别的类的原方法名，看到「A 类的回调里出现 B 类的方法」要按**方法名**而不是类名理解。
- **`Glide.with(BiliTerminal.context!!)` 不会抛「destroyed activity」**：那是 `createConfigurationContext(applicationContext)`，非 Activity → Glide 走 application manager，不做销毁校验。真正会抛的是传 Activity 或传 View（View 的 context 链能追到 Activity）的那些调用点，统一用 `GlideUtil.canLoad(view)` 挡。**更省事的是直接换成 `GlideUtil.with(view)`**（26.11.13 起）：主线程且宿主 Activity 健在时它返回的就是原来那个 Activity 级 manager（暂停/恢复语义不变），页面已 finish/销毁或不在主线程时回落 Application 级 manager 而不抛——`GlideUtil.with(View)` 在 `app/src/main/java/com/RobinNotBad/BiliClient/util/GlideUtil.java:166-175`。**LiveData `postValue` 回包后的 lambda 里最容易漏**（请求期间用户已经退出页面 → `Glide.with(activity)` 当场抛，线上 #309/#295/#310 就是这形态）。

## 基类与列表

- `BaseActivity.kt:282` 用 `if (this !is InstanceActivity) setTopbarExit()` 做**向下判断**——任何「让 `RefreshMainActivity` 继承 `RefreshListActivity`」的方案都会把顶栏行为从「打开菜单」变成「点击即返回」。
- **顶栏箭头 = 页面角色，两者必须一致**（26.10.25 用户明确规则）：**菜单唤起的一级页**用 `arrow_down`（点它打开菜单、在同级页面间切换），**一级页的子栏目**用 `arrow_back`（点它返回上一级）。角色由基类决定——`InstanceActivity` 是一级页（`BaseActivity.kt:584` 给它装 `setMenuClick`），`BaseActivity` 是子栏目（装 `setTopbarExit`）。两条实践：
  1. **图标不再靠布局写**：`InstanceActivity.setMenuClick()` 会按角色把 `pageName` 的开头图标覆盖成 `arrow_down`。因为布局会被两种角色复用——`activity_myspace.xml` 同时喂 `MySpaceActivity`（一级）与 `MySpaceMoreActivity`（子栏目），布局里只能写一个值。
  2. **子栏目别误继承 `InstanceActivity`**：`TodoListActivity`（「设置 → TO DO清单」）就站错队，顶栏点开的是菜单。**判据是「这个页面在不在 `MenuActivity.btnNames` 里」**——不在就是子栏目，继承 `BaseActivity`。
  - 唯一自己管图标的是 `LocalListActivity`（菜单「缓存」）：顶层 `arrow_down`、进文件夹后 `arrow_back`（那时点顶栏是退出文件夹），两次都在基类之后执行，顺序不能反。
- **`cell_video_list` / `cell_dynamic_video` 的 id 是跨包事实协议**：改 id 会同时打破 `PrivateMsgAdapter`、`DynamicHolder`、`NoticeHolder`、`OpusContentAdapter`。
- **`notifyItemRangeInserted` 的起点由 adapter 的 `getItemCount()` 决定，`+1` 多数是"头部占位"**：`ReplyAdapter` / `UserDynamicAdapter` / 系列详情内部 adapter 的 `getItemCount()` 都是 `data.size + 1`，通知起点要 `sizeBefore + 1`；而 `VideoCardAdapter` / `ArticleCardAdapter` / `LiveCardAdapter` 无头部、起点就是 `sizeBefore`。**看到 `+1` 先读 `getItemCount()` 再判越界**（26.10.04 批次 3 修掉 4 处真 bug，详见 `docs/architecture-map.md` §7.9）。
- **adapter 背后的 list「增删」与「对应的通知」必须在同一个主线程 turn 里做完**（26.11.13 线上崩溃 #300）：`ShortVideoPagerAdapter.getItemCount()` 直接返回 `VideoPreloadManager.getItemCount()`（= `allItems.size`），而 `loadInitial/loadMore/loadRelated` 原来在 `CenterThreadPool` 线程就先 `allItems.addAll(items)`、再把 `onItemsLoaded` post 回主线程。于是 `getItemCount()` 抢先涨了、插入通知还没入队，ViewPager2 下一次 layout 就炸 `IndexOutOfBoundsException: Inconsistency detected. Invalid view holder adapter position`（`RecyclerView$Recycler.validateViewHolderForOffsetPosition` ← `ViewPager2.onLayout`）；两批请求交错时两批还会算出同一个 `start = count - items.size`，重复覆盖同一段。修法：`mainHandler.post { if (released) return@post; allItems.addAll(items); onItemsLoaded?.invoke(items) }`。**同一条也要套到 `onDestroyView` 之后**：回调里先取 `val adapter = feedAdapter` 再用同一实例通知，别用 `feedAdapter?.xxx`（取实例与通知之间可能被换掉）。
- **整份替换必须「换 list + 换 adapter」，不在挂着的 list 上原地改**（26.11.13 线上崩溃，收藏夹视频列表页）：`FavoriteVideoListActivity` 原来在 `CenterThreadPool` 线程把新页直接 `add` 进 `videoList`（正是 `VideoCardAdapter` 背后的活 list），回主线程才 `notifyDataSetChanged` / `notifyItemRangeInserted`——`getItemCount()` 抢先涨了、通知还没落地，主线程下一趟 layout 就抛 `IndexOutOfBoundsException: Inconsistency detected. Invalid view holder adapter position`（`RecyclerView$Recycler.validateViewHolderForOffsetPosition` ← `LinearLayoutManager.onLayoutChildren` ← `RecyclerView` 的 `Choreographer` 回调）。**整份替换**（首屏 / 刷新 / 切排序 / 换关键词 / 聚合）一律走「新的 `ArrayList` + 新的 `VideoCardAdapter` + `setAdapter`」（本页收在 `showList()` 一个方法里，顺手把 `selectionMode` 带过去）；**只有翻页**才在原 list 上 `addAll` + `notifyItemRangeInserted`，且这两步必须在同一个 `runOnUiThread` 里做完。同源崩溃：收藏夹管理页 #160、短视频信息流 #300。详见 `docs/architecture-map.md` §7.x「换 list 要换 adapter」。
- **整份重拉要带「代次」守卫，否则在飞的旧页会把新结果糊掉**（26.11.13 同批）：既然换了 list，`clear()` 之后发起的请求、和之前还在路上的旧页，两份结果会先后落到同一份数据上。`FavoriteVideoListActivity` 的做法是 `private var listGeneration`（只在主线程读写，不必 `volatile`）：`loadFirstPage()` 发起时 `++listGeneration` 并把值捕获进闭包，`continueLoading()` 只捕获不增；两者在 `runOnUiThread` 里**先判代数、后落数据**，对不上就丢弃（翻页那条还要顺手 `setRefreshing(false)` 复位 `isLoading`，否则 `goOnLoad` 再也进不来）。`loadAggregate()` 整份换数据时也要 `listGeneration++`，让在飞的翻页一并作废。这是「后台回包再验一次是否还属于当前状态」在 Activity 列表页上的落地，与 `SearchFragment.loadGeneration` 同族。
- **设备档位参数一律从 `PerformanceManager` 取**（图片质量/宽度、分页大小）：`GlideUtil` 里的 `QUALITY_*` / `MAX_W_*` 四个常量已于 26.10.04 删除，**不要在任何调用点重新写死**，否则又变回"两处真相"（详见 `docs/architecture-map.md` §7.10）。
- **后台请求回主线程时，判活要写在 `runOnUiThread` 的 Runnable 内部**，且 fragment 侧要自己补 `isAdded && view != null`（`BaseFragment.runOnUiThread` / `SearchFragment.runOnUiThread` 自 26.10.20 起已在 Runnable 内部统一判活，但**直接 `CenterThreadPool.runOnUiThread { }` 的地方仍要自己补**，别指望投递时判活）。**后台回包落地前还要再验一次「这批结果是不是还属于当前状态」**：光在后台线程比一次不够，检查通过到 Runnable 真正执行之间用户可能已经切了排序 / 换了关键词（搜索页用 SearchFragment.loadGeneration 代次 + 关键词 + 排序三样在 Runnable 内部再验一次）。这是线上 NPE #43–#49 与 ISE #62 的形态：手机/手表都会中，与设备无关。**fragment 里取界面文案优先 `getAppContext().getString(...)`**：detached fragment 上调 `Fragment.getString(...)` 会抛 `IllegalStateException: Fragment … not attached to a context.`（#62 的栈就是 `getString→getResources→requireContext`），详见 `docs/architecture-map.md` §7.44。
- **`MsgUtil.err(e)` 会把任何 `IOException` 换成「网络错误」**（26.10.24 审查发现）：它对 `IOException` 直接 `showMsg(R.string.err_network)` 并 `return`，所以**自定义的 IOException 子类带什么 message 都进不了界面、只进 logcat**。要让用户看到具体原因（如搜索风控），要么在调用侧先判类型单独弹，要么别继承 `IOException`（后者会改动 `throws` 声明，慎选）。现成例子：`SearchFragment.report()` 对 `SearchApi.RiskControlException` 先弹它自己的话。
- **风控不一定回 JSON，「解析成功才判断风控」会漏掉最常见的一种**（26.10.25 审查发现）：B 站被拦时可能直接回一张 `<!DOCTYPE html>` 的「出错啦」页，`NetWorkUtil.getJson` 的 doctype 重试耗尽后抛 `IOException`——此时任何写在 `if (shouldFallback(json))` 里的降级逻辑都没机会跑，用户只会看到「网络错误」。所以判断风控要**同时覆盖请求层失败**（`SearchApi.fallbackToLegacy` 就是为此把主链路的 `IOException`/`JSONException` 也接进回退），但两边都失败时要分清「真断网」与「被拦」——前者如实报网络错误，别诬陷成风控。详见 `docs/bilibili-api-notes.md` §3.13/§3.14。
- **搜索页的搜索框是「盖」在 fragment 上方的，别把新控件加进 `fragment_simple_refresh` 顶部**（26.10.24 实测）：`activity_search.xml` 里 `ViewPager` 只对齐到 `@id/top` 下方，而 `searchbar` 与它同起点、后声明（画在上层）。所以加在 fragment 顶部的任何一行都会**正好压在搜索框里**——排序入口自 26.10.26 起是 `searchbar` 内部最左边的 `searchSortButton`（`ImageView`），fragment 只提供 `sortOptions()` / `currentSortOrder()` / `selectSort()`，控件归宿主。同理：`hasSearched` 之前不显示排序图标。
- **搜索框的滚动收起走 `SearchActivity.onScrolled` 的 `translationY` 旧逻辑，别再引入「动真实高度」的 chrome 联动**（26.10.26 用户要求回退到加排序之前）：26.10.24 曾为「搜索框 + 排序条」共用一条 `ValueAnimator` 动 `layoutParams.height`（`applyTopChrome` + `CHROME_ANIM_MS` + 自然高度缓存），排序入口挪进搜索框内部后整套删掉——`ViewPager` 回到锚 `@id/top`，收起就是 `ObjectAnimator.ofFloat(searchBar, "translationY", 0f, -height)` 配 `handler.postDelayed({ visibility = View.GONE }, 200)`、展开反向，逐字等于加排序功能之前的实现（用户原话「一模一样最好」）。height 用 `searchBar.height + ToolsUtil.dp2px(2f)` 补偿 `marginTop`，节流仍是 `animate_last` 的 200ms 窗口 + `dy < -1` 才展开。
- **搜索框内左侧图标靠 `keywordInput.paddingStart` 让位，别把这 38dp 写死在 XML 里**（26.10.26 实测）：`searchSortButton` 只占 30dp 宽、贴输入框左缘（`marginStart=3dp`），文字要靠输入框自己的 padding 从 8dp 撑到 38dp（`SearchActivity.SORT_ICON_SLOT_DP` = 3dp 边距 + 30dp 图标 + 5dp 间隙）才不钻到图标底下；图标 GONE（没搜过 / 番剧·用户·直播分类）时要把这 38dp 收回去，否则输入框左边空一块。实测（wear5 466×466、密度 2.0）：图标描边占 x=53..88、文字从 x=112 起，互不重叠。亮色模式下搜索框底是浅色（`drawable-notnight/background_searchbar.xml`），图标必须自己会变色：26.11.08 起它是矢量 `drawable/icon_sort_filter.xml` + `drawable-v21/icon_sort_filter.xml`，靠 `android:tint` 取正文色（两份分别是 `@color/text_primary` 与 `?android:attr/colorForeground`），亮暗共用一套、不再需要 notnight 版本（该名已进 `tools/appearance/gen_light_mode.py` 的 `EXCLUDE`）；原先那两份手写 PNG（`drawable-nodpi` 的 `#EBE0E2`、`drawable-notnight-nodpi` 的 `#3A3438`）已删除，改图标只改这两份 XML。
- **`TerminalDialog.singleChoice()` 不会自己 `show()`**（26.10.24 踩到）：它只负责拼装 `AlertDialog` 并 `prepareLayout()`，调用方必须 `.show()`——漏了就是「点按钮只有水波纹、弹窗根本不出现」。另外它的回调**不会自动关闭弹窗**（选集场景要在回调里做越界校验），要自己 `sheet.dialog.dismiss()`。
- **空态浮层必须 `layout_below="@id/top"`，不能盖住顶栏**（26.11.02 用户点名「我的反馈点顶栏不退出、改成刷新」）：`activity_simple_refresh.xml` / `activity_simple_main_refresh.xml` 的 `emptyTip` 是半透明整页浮层，原先 `match_parent` 且排在 `top` 之后——RelativeLayout 后声明的兄弟节点画在上层、触摸也从后往前派发，于是它盖住整条顶栏。**只是在空态时不可点**（没装监听器时点击会穿透回 `top`，所以问题不明显）；一旦页面调了 `RefreshListActivity.setOnEmptyRetry()`（「我的反馈」、公告、收藏、历史、推荐、动态、热搜、直播等），`emptyTip.isClickable=true` 就把顶栏点击全吃掉，退化成「点顶栏重拉列表」。新增同类空态浮层照这两个布局抄，**别写 `match_parent` 顶到 0**；也不要把重试监听装在盖住顶栏的 View 上。§3.103

## 界面与弹窗

- **弹窗（`TerminalDialog`）的按钮必须一个按钮占一整行，别横排两个窄按钮**（26.11.13，控制台反馈 #161，同族 #125 / #54）：老写法是「按钮行 `gravity=end` + 两个 `wrap_content` TextView」，在 466×466 手表屏上实测按钮只覆盖 `x167..301` 与 `302..411`，**按钮行左侧 144px、右侧 30px 是死区**（点上去前后截图逐字节相同）。这类手表 ROM（HUAWEI HWARC、hesc sl8541e 等）存在输入坐标整体右移约半个按钮宽的偏移（#54 原话「点击屏幕上的按钮时触控会判定到旁边的位置」），于是「点取消」落到删除、「点移除」落到右侧死区毫无反应。改成整行宽的纵向堆叠后，点该行**任意 x** 都命中同一个按钮，偏移不再有害。**新增弹窗别手拼横排按钮**；`app/src/main/res/layout/activity_input_dialog.xml:50-72` 是整页输入页的同款横排（`FollowUsersActivity` / `LocalListActivity` / `PlayerActivity:1985` 在用），尚未改，动它前先读 `docs/architecture-map.md` §8.7.0。
- **别再用「量一遍再改尺寸」的办法适配弹窗按钮**（26.11.13 已整段删除）：`fitButtonBars()` / `fitButtonBar()` / `barDesiredWidth()` / `shareBarWidth()` 那套逐轮改 padding、缩字号、改 `weight` 的兜底，本身就是「窗口尺寸与内容尺寸两份账」的可疑来源，也是 #125 长期误判成「测量时序」的根源。按钮行交给普通 `MATCH_PARENT` 布局，放不下就由 `DialogSizing.plan()` 压滚动区高度。要看按钮真实几何时调 `Sheet.logButtonGeometry()`（走 `Logu.w("dialog", …)`，会随用户反馈附带的日志送上）。

## 崩溃页 / 通知 / 下载

- **崩溃页跑在 `:error_activity` 独立进程**（26.10.04 起）：`CatchActivity` 不经过 `PerformanceManager.init` / `ErrorCatch.init` / 未读轮询 / 更新检查，加依赖前先确认它不需要这些初始化；判进程用 `BiliTerminal.currentProcessName()`（读 `/proc/self/cmdline`，`minSdk 19` 用不了 API 28 的 `Application.getProcessName()`）。
- **任何"把 APK 交给系统安装器"的路径都必须先过 `ApkVerifier.verify(context, apkFile)`**（26.10.04 批次 4 新增）：现有两条链路（`UpdateManager.downloadApk`→`installApk`、`DownloadActivity.installApk`）都已接线；下载链路上校验失败要**删掉残片**，否则下次 `Range` 续传会把它当成"已下载一部分"。判定为「包名一致 且 签名集合一致」，**读不到签名一律失败关闭**（详见 `docs/architecture-map.md` §7.11）。
- **分片（Range）下载必须校验「服务端回的是不是这一段」，只看 HTTP 2xx 会静默产出坏文件**（26.10.25 修复用户反馈的「多线程下载拼不起来 / 卡在 20%」）：`DownloadService.downloadSegment` 靠 `Range: bytes=start-end` + `RandomAccessFile.seek(start)` 写入，服务端若忽略 Range 回 200（整个文件）或 206 但区间起点不对，客户端仍会从 `seek(start)` 写下去，**字节数还可能正好对得上**，校验通过、文件却错位。判据收在 `service/download/SegmentDownloadPolicy`（`internal object` 纯逻辑 + 8 例单测）：`isRangeIgnored` / `isPartialContent` / `isContentRangeMismatch` / `hasStalled` / `shouldDisableSegmentMode`。三条同源要求别漏：读循环只能写本片范围内（`written < expectLen`，超发会覆盖下一片）；**`join` 超时后绝不能直接回退单线程重下**——残留分片线程还在写同一个文件，`FileOutputStream` 会截断重写，两边抢写就是坏文件（先 `Call.cancel()` + `aborted` 让它们收尾，排不空就判失败）；全部写满后仍要校验 `file.length() == totalSize`（`setLength` 在部分 FUSE/exFAT 上会静默失败）。
- **通知 ID 不要重号**（26.10.04 批次 5 起有四处）：`DownloadService` = 1027、`PlaybackService` = 1028、`util/MsgNotifier.kt` 新消息 = 1029、同文件追番更新 = 1030。**新消息提醒只在"未读变多"时弹一次**（`MsgNotifier.shouldNotify`，纯函数有单测），触发点是 `BiliTerminal` 既有的未读检查，项目**没有也不需要 WorkManager/AlarmManager**；Android 13+ 的 `POST_NOTIFICATIONS` 在消息页申请，未授权时通知静默不弹（不是 bug）（详见 `docs/architecture-map.md` §7.15）。
- **追番更新提醒靠"最新集 id 快照"判据**（26.10.04 批次 5 的 C16）：只看同一部番的 `new_ep.id` 是否变化（不用总集数、更不用服务端的 `is_new`），快照是 `SharedPreferencesUtil.BANGUMI_UPDATE_SNAPSHOT` 里 `{"media_id": new_ep_id, …}` 的整份 JSON；**首次检查只写快照不提醒、这次新追的番不算更新、拉取失败绝不覆盖快照**（改这三条语义前先看 `util/BangumiUpdateChecker.kt` 与 `docs/architecture-map.md` §7.16）。拉取上限 10 页 × 30 条，`ps` 定义域就是 1-30。
- **`DownloadService` 已按关注点拆分**（26.10.04 批次 8 的 E2）：实现分居 `service/download/`——`DownloadPathSpec`/`DownloadProgressMath`（纯函数）、`DownloadProgressStore`（进程级状态，`internal object`）、`DownloadRepository`（DB）、`DownloadNotifier`（通知，普通 class 持 Service 引用），对外 `@JvmStatic` API 一字未改。改下载代码前记住三条：**`start(Long)` 的 `@JvmStatic @Synchronized`（锁 Companion）与 `DownloadProgressStore.speedLock` 是两把不得互换/合并的锁**；`pausedMap` 必须仍是同一个 `ConcurrentHashMap` 实例（`DownloadListActivity` 直接对它 add/remove）；`speedStr`/`isSpeedMode`/`activeDownloadsCount` 刻意保持**非 volatile**（既有数据竞争，别顺手加）（详见 `docs/architecture-map.md` §7.27）。
- **`<shape>` 里不许写 `?attr/…` 当颜色**（26.11.08 修用户报的「26.11.07.1 启动即崩」）：`minSdk 19` 时 API<21 的 `GradientDrawable.inflate` 只认具体颜色，`TypedArray.getColor` 碰到 `type=0x2`（TYPE_ATTRIBUTE）抛 `UnsupportedOperationException: Can't convert to color: type=0x2`，再被 `Resources.loadDrawable` 包成 `Resources$NotFoundException: File res/xx.xml from drawable resource ID #0x…`——**release 包资源名被混淆（`res/uU.xml`），栈里根本看不出是哪个 drawable**，得拿 `aapt2 dump resources <apk>` 把那个 `0x7f…` ID 查回名字（本次 `0x7f0800a2` = `drawable/dialog_background`）。仓库惯例：**`drawable/` 给 API<21 用的具体颜色**（跟着 `values`/`values-notnight` 的色值自动亮暗），**`drawable-v21/` 才保留 `?attr`**。本批修掉三处：`drawable/dialog_background.xml`（每个 `TerminalDialog` 的背景；启动时只要弹隐私同意框就在 `onCreate` 里崩）、`drawable/background_card.xml`（播放页卡片，自 Initial commit 起就带主题属性）、`drawable/zoom_btn_bg.xml`（验证码页缩放按钮）。**新增 shape 一律照这个结构放两份**；排查用 `grep -rn "?attr/" app/src/main/res/drawable*`，落在 `<solid|stroke|gradient>` 上的都要处理（`layout/` 里的 `?attr` 是运行时解析、`drawable-v21/` 里 vector 的 `android:tint="?attr…"` 都正常，别一起改）。

## 播放器与弹幕

- `player/` 包不是公共层：`VideoPlayerCore.kt` 已是 `IjkPlayerBridge` 的功能超集，但**还不能直接替换**——`PlayerState`/`IjkOption` 仍定义在 `IjkPlayerBridge.kt:17-36`（删旧类前先搬家），且 `VideoPlayerCore.release()` 有一次性 `released` 标志，`onViewRecycled` 后复用会**泄漏 native 播放器**。动手前先决定它的去留，含糊着抽公共层会造出第 3 套实现。
- **手表右滑返回由 `android:windowSwipeToDismiss` 控制**，它在窗口层直接 `finish()`，**不走 `onBackPressed`**，所以只 override `onBackPressed` 拦不住。且 `onCreate` 里的 `setTheme(ColorScheme.themeResId(theme))` 会覆盖清单上声明的 `Theme.NoSwipe*` —— 要真正禁用它，必须调 `ColorScheme.themeResId(theme, noSwipe = true)` 换用 `Theme.*.NoSwipe.AppCompat`（issue #1 的根因）。26.10.22 起**播放页 `PlayerActivity` 无条件走 noSwipe**（用户要求：播放页禁止右滑退出，不设开关）；其他页面仍由「禁用返回键」或各自的 `forceNoSwipeTheme` 决定。noSwipe 只换窗口属性，不影响应用自己处理的手势（滑动调进度、缩放拖动等）。**它对两类「右滑」天然无效，别以为改成 noSwipe 就万无一失**：① 用「模拟按下返回键」实现右滑的手表（设置的「禁用返回键」说明里点名米兔等）——到应用侧就是一个 `KEYCODE_BACK`，与物理返回键不可区分，只有连返回键一起拦才拦得住；② 手机/平板的系统返回手势（窗口属性不参与），要拦得用 API 29+ 的 `setSystemGestureExclusionRects`，仓库目前没用、也没真机验证（26.10.22 用户拍板：这两类都保持现状，播放页返回键仍可退出）。
- **弹幕时间轴只能由播放器位置驱动**（26.10.22）：DFM 原生 `syncTimer()` 用墙钟计时，播放速率不是 1.0x 时会与画面**速率性发散**（实测 0.9x 播放时每 4 秒差 490ms），以前靠周期性 `seekTo` 吸附，而 `seekTo` = 清屏重建，表现就是「弹幕每隔十来秒闪一下又没了」。现在由 `DanmakuManager.bindMediaClock()` 绑 `video_now`（`DanmakuFlameMaster` 的 `MediaClockSync` + `DrawHandler.MediaClock`），**不要再加周期性纠偏**；`MediaClock` 跑在渲染线程，只能读主线程采样好的 `@Volatile` 值，不许调 `currentPosition`（详见 `docs/architecture-map.md` §7.51）。
- **播放页必须自己保亮屏，且用窗口标志**（26.10.22）：长视频页靠 `activity_player.xml` 的 `android:keepScreenOn="true"`，短视频页原先漏了（看到一半熄屏）。新播放页要用 `window.addFlags(FLAG_KEEP_SCREEN_ON)` 并按「当前活跃播放器是否真在播」**整体重算**，`onStop` 兜底清；View 级 `keepScreenOn` 在 RecyclerView item 上清不干净。26.11.01 又补三道闸：**前台判据**（`isForeground`，`onStart`/`onStop` 维护；判据链穿四层，页面不可见时 prepare 完成也会把 `isPlaying` 置真）、**`onResume` 兜底重算**（`onStart` 那次必然早于 Fragment 的 `onResume`，算出来是 false）、**`isPlaying` 与 `playerBridge.isPlaying` 真值对齐且 `play()` 在 `!isPrepared` 时不许置真**（否则取流失败会永久亮屏）。详见 `docs/architecture-map.md` §7.52。
- **短视频画面尺寸要由 `PlayerState` 驱动，不能只在 `onPrepared` 算一次**（26.11.01）：`videoWidth/videoHeight` 来自容器 `codecpar`，mediacodec 路径下缺失就是永久 0，`adjustVideoSize()` 早退会让 `TextureView` 留在 `MATCH_PARENT`（画面被拉伸铺满整屏）。尺寸变化要在 state 采样里消费、旋转 90/270 要交换宽高、未知尺寸要退化比例而不是留 `MATCH_PARENT`；纯计算在 `activity/video/ShortVideoLayoutMath.kt`（有单测）。详见 `docs/architecture-map.md` §7.58。
- **本地缓存/下载文件交给外部播放器时，别只信 FileProvider**（26.11.01）：FileProvider 的根来自 `res/xml/file_paths.xml`，而它支持的 tag 全只认主卷（`<external-media-path>` 只取 `getExternalMediaDirs()[0]`）。用户把「缓存路径」改到 SD 卡后 `getUriForFile` 抛 `IllegalArgumentException: Failed to find configured root`，点缓存视频直接崩。现在**只有凉腕分支**（`PlayerApi.getVideoUri`，仅本地文件会走）会回落 `util/LocalFileProvider`（运行时按所有卷算根，`util/SharedFilePolicy` 判归属、有单测），再失败回落内置播放器；小电视分支仍传裸路径（历史行为，本次没动）。**别再往 `file_paths.xml` 里加 `<root-path>` 兜它**（审计 M12-e 删的就是它）。详见 `docs/architecture-map.md` §7.59。
- **`PlayerData.mid` 是登录账号，不是视频作者**（26.11.06 修）：连播「按 UP 主投稿」要的是作者，作者单独走 `PlayerData.uploaderMid`（由 `VideoInfo.toPlayerData` 从 `staff[0]` 填，随 Intent / 会话哨兵一路传进播放器）。两者历史上共用一个字段，结果连播拉的是登录账号自己的投稿、连播层标题也变成自己的昵称。判据收在 `player/PlayerQueueAuthorPolicy`（有单测）：作者未知（0）时按 aid 现查 `x/web-interface/view`，**任何情况下都不许退回登录 mid**；切到别的条目 / 进分P层要按新 `videoInfo` 重新定稿（允许 0），否则会沿用上一条视频的作者。
- **原生库加载一律走 `player/IjkNativeLibs.ensureLoaded(context)` 并判返回值**（26.10.19 线上崩溃 #48）：`loadLibrariesOnce` / `IjkMediaPlayer()` 失败抛的是 `UnsatisfiedLinkError`（`Error`，`catch (Exception)` 兜不住），且构造内部会二次加载库。该类已做「失败即锁死 + 诊断写 `Logu` + 按隐私开关上报」，`PlayerActivity` / `IjkPlayerBridge` / `VideoPlayerCore` / `ShortVideoPlayerActivity` 均已接线，**新代码不要再裸调 `loadLibrariesOnce` / `IjkMediaPlayer()`**（详见 `docs/architecture-map.md` §7.44）。
- **弹幕 XML 解析是懒执行的**（26.10.20 修）：交给 `DanmakuManager.createParser` 的流不能在该方法返回后关掉——真解析在 `DanmakuView` 渲染线程（`DrawTask.java:283`），`BiliDanmukuParser.parse()` 读到已关闭流会 `return null`，弹幕**静默全空**（26.10.02 的 `use{}` 就这样弄空了所有本地缓存视频的弹幕）。要传流就传 `ByteArrayInputStream`（close 是空操作），或先把内容读进内存（详见 `docs/architecture-map.md` §7.46）。
- **播放页里的「输入型」交互不要另开 Activity，用页内卡片**（26.11.14 修）：`PlayerActivity` 一旦被别的 Activity 整页盖住，`SurfaceView` 的 Surface 就被销毁，回来要靠 `PlayerSurfaceBinder.onSurfaceReattached` 重新 attach + `seekTo` + 重设几何才能出画，这条路**在手表上并不总成功**——「跳到指定时间」原来就是 `startActivityForResult(InputDialogActivity)`，用户报「跳完回来画面没了」。现在改成与「发送弹幕」同构的 `jump_time_card`（`activity_player.xml` 里 `layout_card_bg` 下的居中卡片：标题 + 单行 `EditText` + 整行确认按钮），卡片互斥由 `showJumpTimeCard()` / `btn_danmaku_send` 点击里互相 `GONE` 保证，统一收起走 `hideAllCards()`。**新增播放页交互照这个形状做**；只有必须跳页的（如设置）才用 Activity，且要接受回来可能黑屏。注意单行 `EditText` 会踩 `focusSearch` 的 ISE，`dispatchKeyEvent` 里的 `EditorEnterKeyGuard` 必须继续兜住（线上崩溃 #66）。

## 伪装与顶栏手势

> 需求与验收口径见 `docs/superpowers/specs/2026-10-22-disguise-mode.md`。这一节只记「踩过就会出事」的那几条。

- **双击顶栏必须自己接管触摸，别只挂 `OnDoubleTapListener`**（26.10.22）：双击的**第一次抬手已经是一次完整 click**，页面会先 `finish()`，第二次点击根本落不到同一个 View 上。正确做法是 `OnTouchListener` 返回 `true` 消费全部触摸、事件喂 `GestureDetector`，单击 / 长按再用 `performClick()` / `performLongClick()` **回放**给各页面自己装的监听器（实现只有 `util/DisguiseGesture.kt` 一份，详见 `docs/architecture-map.md` §7.53）。**别改成「在单击监听器里判断两次点击」**——第一次点击已经执行完了，那会变成「退出两次」。
- **在 `OnTouchListener` 里做长按计时，`ACTION_DOWN` 必须返回 `true`**（蓝牙伪装页的教训）：返回 `false` 时 View 没成为触摸目标，系统不再派发 `UP` / `CANCEL`，`removeCallbacks` 永远执行不到 → **轻点一下，2 秒后窗口自己 `finish()`**，伪装直接失效（`BluetoothDisguiseActivity.setupExitGesture`）。返回 `true` 时若要保留点击语义，得自己补 `performClick()`。
- **顶栏延迟装载必须封顶**：`asyncInflate` 页面在 `onStart` 时 `findViewById(R.id.top)` 还是 null；但**有 11 个页面布局里根本没有 `R.id.top`**（Download / Catch / Tutorial / TutorialPager / JumpToDialog / InputDialog / CaptchaWebView / QRLoginRegister / ConfirmDialog / Dialog / ListDialog），无上限 `post` 会在这些页面里每帧投递一次、耗电到页面结束。现在封顶 20 次 × 50ms 并在放弃时打日志。**开开关进这些页面只该看到一条日志**，多了就是又没封顶。
- **接线点三个，装和摘都要做**：`BaseActivity`（普通页）、`PlayerActivity.onStart`（**不继承** `BaseActivity`）、短视频 `PageHolder.syncDisguiseGesture()`（顶栏在分页 item 里）。只 `install` 不 `detach` 的话，开关关掉后已装上的触摸层不会自己消失，必须重进页面才失效。
- **伪装页的暗号只允许 4~8 位数字**：计算器上敲不出字母，配了 `abc` 就是把自己锁在伪装页里、只能强杀应用。`DisguisePrefs.normalizeCode` 拦一次、`code()` 读取侧再兜一次，**别为了"支持复杂暗号"放开这两个校验**。
- **长按监听器 `return true` 就必然会震一下，模式能管住动作、管不住手**（26.11.11 修反馈 #153，PR #27）：AOSP `View.performLongClickInternal` 是 `if (handled && shouldPerformHapticFeedback) performHapticFeedback(LONG_PRESS)`，`handled` 只看回调返回值——所以「模式不允许、`return true` 把手势吞掉」这种写法**必然附带一次震动**，框架分不清「真执行了动作」和「只是把长按吃掉」。要静音只能在长按触发**之前**把 `topBar.isHapticFeedbackEnabled` 置 false（`isPerformHapticFeedbackSuppressed` 判的就是它），`BaseActivity.syncTopbarLongPressHaptic()` 在 `setupTopbarLongPressToHome()` 里每次 `onStart` 按本页判据同步（`handlesTopbarLongPress()` 决定走 `isEnabledForVideoPages()` 还是 `isEnabledForNormalPages()`）；**别把同步挪进 `onCreate` 或搬回「按下时读模式」的思路**——View 开关只能提前设，且设置页改完回来必走 `onStart`，与按下时读模式等效。伪装回放（`DisguiseGesture` 里的 `topBar.performLongClick()`）用的是同一个 View，一样受这个开关管。详见 `docs/architecture-map.md` §7.53。
- **顶栏时钟不能包在 LinearLayout 里**（26.11.01）：`BaseActivity.setRound()` 的圆屏适配靠给 `@id/timeText` 加 `RelativeLayout.CENTER_HORIZONTAL` 把时钟挪到顶栏正中；父容器不是 RelativeLayout 时 `newTopbarParams()` 会按真实父容器造船型（**所以不崩、也不报错**），但那条居中规则根本加不上去 → **静默失效**。`activity_simple_main_refresh.xml` 曾把时钟额外套在一层 `menuArea`(LinearLayout) 里，结果首页 / 推荐 / 全站排行榜 / 热门 / 入站必刷 / 本地列表这 5 个页面在圆屏模式下时钟一直钉在最右、被圆盘切掉。**新增或改顶栏布局照 `activity_simple_refresh.xml` 抄**：时钟是 `@id/top`(RelativeLayout) 的直系子 View，标题用 `layout_toStartOf="@id/timeText"`。
